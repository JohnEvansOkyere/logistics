# Project audit — engineering and shipping view (2026-09-29)

Scope: client material (`client_message_extract.md`, `second_meeting_message.md`, `adress.md`, `EVIDENCES/`), project instructions and docs (`AGENTS.md`, `README.md`, `docs/*`, `CHECKLIST.md`, `MEMORY.md`, `questions.md`), and the codebase at `main` plus the uncommitted working tree. Client documents were read locally only; this report records structure, not client values.

Checks run during the audit: `pnpm lint` (pass), `pnpm typecheck` (pass), `pnpm test` (31/31 pass), `pnpm test:e2e` (31/31 pass — same files as `test`, see E9), `pnpm format:check` (fails on `AGENTS.md` only). Running local stack: API health `ok` on PostgreSQL, unauthenticated API calls return 401, web routes render.

## 1. Executive summary

**What the client asked for:** one place to run and retrieve every job file — register a file number, track the shipment, bill, record payment, clear, deliver, collect proof of delivery/EIR, close — for sea/air import/export, plus warehousing and road transport. Their stated pain is concrete: _"yearly or three years job when we are looking for documents we can't even find it"_ and updates scattered across email and WhatsApp.

**What exists:** a well-documented, security-conscious foundation. Staff auth, super-admin account lifecycle, customer companies/contacts, company-scoped access, quote requests, free-text quote drafts with revisions, and manual department assignment. Tests pass; access boundaries are tested at the database (pgTAP) and API level.

**The gap:** none of the product's core object exists yet — no **job/file**, no **milestones**, no **document upload/archive**, no **invoice/payment records**, no **waybill/POD/EIR**, no **notifications**. By requirement count, roughly P01 and P02 are partially built; P03–P14 are not started. Measured against the client's own words, the system cannot yet do the first thing they described ("we register the file and give them a file number").

**Headline recommendation:** re-sequence toward a thin, usable **Release 1 = "the job file"**: job registration with file number → milestone timeline → private document archive with search → manual ETA → staff-recorded invoices/payments. That directly addresses the pain the client named, and everything else (portal, OCR, SMS, carrier tracking) hangs off the job. This is a recommendation, not a decision; see §4.

## 2. Engineering point of view

### 2.1 Strengths worth keeping

- **Architecture is right-sized**: modular monolith (Next.js + NestJS + Supabase Postgres/Auth/Storage), API-only business data, private `app` schema with grants revoked from `anon`/`authenticated`. No premature microservices.
- **Authorization is taken seriously**: JWT verification server-side, company scoping on queries, known-ID denial tests, live local Postgres/Nest isolation test, pgTAP suite (62 assertions), single-`super_admin` invariant enforced in the database.
- **Audit-first data design**: role history, membership history, draft revisions and assignment history are append-only (immutability triggers in SQL).
- **Discipline around client data**: client files are gitignored; decisions are logged with dates and rejected alternatives.

### 2.3 What the evidence tells us about the data model

Structural observations from `EVIDENCES/` (no client values copied):

- **Quotes:** per-container-size columns, charge basis per line, "at cost" pass-through lines with indicative amounts, currency stated (samples in both USD and GHS), document requirements, 3–5 business-day timeline, reference pattern like `BJH/SEA/…`.
- **Third-party supplier invoice (port services):** line items with qty/unit cost, Ghana levies and VAT itemised separately, total in GHS, "USD charges payable in GHS at prevailing rate", e-VAT status. → The system must store **supplier invoices as disbursement evidence**, distinct from BJH customer invoices, and support **exchange-rate capture**.
- **House documents BJH issues:** house bill of lading and house air waybill with BJH-prefixed numbers, linked to a master B/L / MAWB; consolidated air manifest listing house bills under one master. → Model `shipment_reference` with master/house hierarchy; one master can carry many houses (consolidation) — this is not in `docs/data-model.md` yet.
- **Proof of delivery:** AWB reference, consignee, packages/weight, date/time, receiver name/phone/signature, stamp. Scanned.
- **Letterhead/identity:** registered address, VAT number, phone, email — belongs in configurable issuer settings (D03), never hard-coded.

### 3.3 Suggested release shape (for discussion)

- **Release 1 — Job file (staff only):** customers, jobs with file numbers (sea import first, D01 permitting), milestone timeline with evidence, private document upload/archive/search, manual ETA, supplier-invoice/disbursement upload, staff notes. Quotes can stay as uploaded PDFs.
- **Release 2 — Money and paperwork:** structured quotes → issue → accept → job; customer invoices; staff-recorded payments/receipts; waybill/POD/EIR generation; closure gates. Remaining sea/air flows.
- **Release 3 — Client-facing:** customer accounts, portal (own jobs, documents, invoices, quote requests), email + SMS notifications.
- **Release 4 — Automation and other services:** OCR-assisted extraction, carrier adapters, warehousing, standalone road, WhatsApp.

This departs from the current delivery-plan order (which puts quote issuance/acceptance ahead of jobs). It is a proposal for Evans to accept or reject.
